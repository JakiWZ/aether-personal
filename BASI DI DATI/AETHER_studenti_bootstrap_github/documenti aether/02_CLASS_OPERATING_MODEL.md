# Modello operativo — AETHER Software Company

## Ruoli

### Product Owner / Cliente
Docente.

Responsabilità:
- spiega il problema;
- chiarisce requisiti;
- ordina il backlog per valore;
- accetta o rifiuta il risultato durante la Sprint Review;
- introduce Change Request e nuovi vincoli.

Non deve necessariamente avere un account GitHub.

### Scrum Master
Uno studente, a rotazione ogni Sprint.

Responsabilità:
- fa partire il Daily;
- protegge il timebox;
- evidenzia impedimenti;
- facilita Planning, Review e Retro;
- non assegna il lavoro come un capo.

### Development Teams
Cinque squad cross-functional.

Ogni squadra deve ragionare sull'intera vertical slice:
DB → Backend → API → Frontend → Test → Documentazione.

## Le 5 squad

| Squad | Dominio principale |
|---|---|
| ARES | Colonie, habitat, astronauti e competenze |
| PHOENIX | Missioni, equipaggi e pianificazione |
| TITAN | Rover, veicoli, stato e manutenzione |
| ORION | Risorse, stock, movimenti e logistica |
| HELIOS | Incidenti, alert e risposta operativa |

## Regola assenze

L'assenza di uno studente non deve bloccare una Story.

Ogni Story deve avere:
- almeno 2 persone che ne conoscono il contesto;
- note nella Issue;
- branch remoto aggiornato;
- nessun file importante conservato solo sul PC locale.

## Tre Sprint

### Sprint 1 — FOUNDATION
Goal: rendere AETHER tecnicamente avviabile e consegnare una prima vertical slice per dominio.

### Sprint 2 — CORE OPERATIONS
Goal: sviluppare le principali regole di business e integrare i domini.

### Sprint 3 — INTEGRATED MVP
Goal: completare i flussi end-to-end, correggere bug, migliorare qualità e preparare la demo finale.

## Non tutto il backlog deve essere chiuso

Un backlog vero contiene più lavoro di quanto entri negli Sprint.

Durante il Planning gli studenti devono scegliere cosa è realistico completare e imparare a dire **no** al lavoro eccessivo.
